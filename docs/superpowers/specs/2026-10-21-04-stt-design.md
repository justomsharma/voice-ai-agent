# 04_stt — Design Spec

Date: 2026-10-21
Status: Approved in conversation ("build the complete stage 4, don't ask")

## Purpose

Turn audio into words, and show what happens in between: the audio format
the API expects, how the bytes travel, how long each part takes, and how
wrong the words are. Three steps:

- **A. Batch:** WAV file → one HTTPS request → transcript, latency breakdown, WER.
- **B. Streaming:** mic (or a WAV played in real time) → WebSocket → partial
  text while you speak, final text after Stage 03's VAD says you stopped.
- **C. Evaluate:** a folder of recordings + reference texts → WER and
  latency per file and per provider.

No LLM, no TTS, no full agent pipeline.

## Provider choice (docs checked 2026-10-21)

| | OpenAI | Deepgram |
|---|---|---|
| Batch model | `gpt-transcribe` (recommended; `whisper-1` / `gpt-4o-*-transcribe` deprecated, shut down 2027-02-26) | `nova-3` |
| Batch contract | multipart form, `file` + `model` + `languages[]`; wav/mp3/…; ≤ 25 MB | raw audio bytes as the body, `Content-Type: audio/wav`, options in the query string |
| Live model | `gpt-live-transcribe`, WebSocket, PCM16 **24 kHz** base64 in JSON events | WebSocket, raw binary PCM, `is_final` / `speech_final` |
| Live turn detection | **none** (`turn_detection: null`): the client must commit each turn | server-side endpointing |

**Primary: OpenAI.** One key covers batch and live. And because
`gpt-live-transcribe` has no server VAD, *our own Stage 03 VAD decides when
to commit a turn*, which is exactly the VAD↔STT integration lesson. Its
24 kHz input also forces a real resampling step.

**Second batch adapter: Deepgram `nova-3`.** Small (one POST), and its
contract (raw bytes, query options) contrasts with OpenAI's multipart. It
proves the interface works for more than one provider, and Step C can
compare them on the same audio.

Not chosen now, and kept for later benchmarks: Deepgram Flux (conversational
STT with turn-taking, overlaps Stage 08), Sarvam (Indian languages / Hinglish),
AssemblyAI, and local Whisper.

## Constraints

- Python + numpy, as in Stages 01–03. HTTPS through stdlib `http.client`, so the
  connect / upload / wait / download times can be measured separately. The
  multipart body is built by hand, so it can be printed (`--dry-run`).
  One new dependency: `websockets` (sync client) for Step B.
- Keys come from environment variables or a git-ignored `.env`. They are never
  printed. `.env.example` is committed.
- Tests use fake HTTP and WebSocket transports: no key, no network, no mic.
- Reuse `01_audio` (wav_io, AudioFormat) and `03_vad` (EnergyVad, analyze).

## Key behaviours

- **Resample, never relabel.** `resample()` is a band-limited (Kaiser-windowed
  sinc) interpolator, so 48 kHz → 16 kHz removes content above 8 kHz instead
  of aliasing it. `--relabel-rate` exists *only* as an experiment, to hear
  what lying about the rate does to the transcript.
- **Validation before paying:** empty audio, < 0.1 s, > provider size limit,
  and unsupported WAVs are errors. Near-silent audio (peak < -60 dBFS) is a
  warning, because models can hallucinate text from silence.
- **Errors:** `SttError(kind, message, retryable)`, where kind is auth /
  rate_limit / bad_request / server / timeout / network / empty_audio /
  bad_response. Rate-limit, server, timeout and network errors are retried
  twice with backoff (`Retry-After` honoured, capped).
- **Batch latency:** prepare, connect (TCP+TLS), upload, wait (server
  processing, until the first byte), download, plus RTF = request time ÷ audio
  duration.
- **`--vad` (batch):** Stage 03 trims to speech segments before upload.
  The trade-off is a smaller payload versus the risk of chopping quiet words,
  which shows up as WER deletions.
- **Live gate:** a ring buffer keeps `pad_ms` of pre-roll. Audio is sent from
  VAD STARTING, `clear` on a false start, and `commit` at segment end.
  `--no-gate` sends everything (the cost vs accuracy comparison).
- **Live board:** deltas build a provisional (partial) text per item; `completed`
  replaces it with committed (final) text. Finals may arrive out of
  order, so `item_id` maps them back to turns.
- **Live timings per turn:** time to first text (from first audio sent),
  final after commit, and final after your last loud frame (this includes VAD
  min-silence).
- **Missing or late finals:** wait `--final-timeout` s, then report
  which turns never finalised. A dropped socket ends the run with the text
  received so far and an error line.
- **WER** = (S + D + I) / reference words, after normalisation (lowercase,
  punctuation stripped, Unicode-safe for Devanagari). Corpus WER sums the
  errors across files instead of averaging per-file WERs. CER is reported too,
  for Hindi/Hinglish spelling variation.
