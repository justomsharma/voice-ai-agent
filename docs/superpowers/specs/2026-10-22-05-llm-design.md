# 05_llm — Design Spec

Date: 2026-10-22
Status: Approved in conversation ("build stage 5, let me know when it's completely built")

## Purpose

Turn a transcript into a reply, and show what happens in between: the
instructions, the history we resend each turn, the bytes on the wire, how
long the first word takes versus the whole answer, and how many tokens it
cost. Four milestones:

1. **Basic call:** text in → complete reply out (`chat.py "..."`).
2. **Prompt experiments:** same questions, different instructions → compare
   length, speaking time, markdown, latency (`experiment.py`).
3. **Multi-turn:** history we manage ourselves, so "What about tomorrow?"
   works; `--no-history` shows it failing (`chat.py`, `history.py`).
4. **Streaming + benchmarks:** text as it arrives, TTFT vs total, time to
   first sentence, and a small repeatable eval set (`stream.py`, `llm_eval.py`).

No tools, RAG, TTS, LiveKit, Pipecat or full voice pipeline.

## Provider choice (docs checked 2026-10-22, wire format verified with real calls)

- **API:** OpenAI Responses API, `POST https://api.openai.com/v1/responses`.
- **Default model:** `gpt-6-luna`, OpenAI's "fastest and most cost-effective"
  model ($0.10 / $0.50 per 1M input / output tokens). It supports
  `reasoning.effort: "none"`, which we use by default: a voice reply should
  start fast, and reasoning tokens are generated (and billed) before the
  first visible word. Its default effort is `medium`, so we always send it.
- `temperature` / `top_p` are only accepted when effort is `none` (verified:
  400 "Unsupported parameter: 'temperature'" otherwise). We refuse that
  combination locally, before paying for a round trip.
- `store: false`: we keep the history ourselves and resend it. The
  server-side alternatives (`previous_response_id`, `conversation`) are
  documented, not used, because the lesson is seeing what the model is sent.
- Verified wire format: request `{model, instructions, input: [{role,
  content}], reasoning: {effort}, max_output_tokens, store, stream}`;
  response `{id, status: completed|incomplete|failed, incomplete_details:
  {reason}, output: [{type: message, content: [{type: output_text, text}]}],
  usage: {input_tokens, input_tokens_details: {cached_tokens},
  output_tokens, output_tokens_details: {reasoning_tokens}, total_tokens},
  error}`. Streaming is SSE (`event:` + `data:` lines, blank line between
  events), with `response.output_text.delta` carrying `delta`, ending in
  `response.completed` / `response.incomplete` / `response.failed`, or an
  `error` event. No `[DONE]` sentinel. HTTP errors come back as JSON
  `{"error": {message, type, param, code}}` even when `stream: true`.

## Constraints

- Same style as Stage 04: stdlib `http.client`, so connect / wait / first
  text / total can be timed separately; SSE parsed by hand. No new
  dependencies (no SDK).
- Provider code lives in one file (`openai_llm.py`) behind a small interface
  in `llm.py`, so another provider is a new file plus a registry entry.
- Keys from the environment or the git-ignored `.env` (Stage 04's
  `load_env_file`), never printed. `--dry-run` shows the request without a key.
- Tests use fake transports and a fake client: no key, no network, no cost.
- Module names must not collide with other stages on `sys.path`
  (04_stt has `evaluate.py`, so ours is `llm_eval.py`).

## Key behaviours

- **Reply is only "complete" on `status: completed`.** `incomplete` (e.g.
  `max_output_tokens`) is returned but flagged and never saved to history.
  A stream that ends without a terminal event, a `response.failed`, or an
  `error` event raises `LlmError` carrying the partial text seen so far,
  so a half answer is never mistaken for a whole one.
- **Errors:** `LlmError(kind, message, retryable, partial_text)`, kind =
  auth / rate_limit / bad_request / server / timeout / network /
  bad_response / stream_cut / failed. 429 "insufficient_quota" is not
  retryable. Retries (exponential backoff, Retry-After honoured, capped)
  happen **only if no text has been shown yet**: a retry after half an answer
  was printed (or, later, spoken) would repeat it.
- **Timings:** connect (DNS+TCP+TLS), wait (request sent → response
  headers), first text (from request start, what the user feels), total.
  Non-streaming: first text = total, which is the point of streaming.
  `stream.py` also reports time to first complete sentence, which is the
  earliest moment Stage 06 TTS could start speaking.
- **History:** `Conversation` holds user/assistant turns. Each turn sends
  instructions + all kept turns + the new message. A turn is committed only
  after a completed reply. On error or incomplete reply, the user message
  is rolled back. Trimming drops the oldest whole turns, by `max_turns`
  and/or an estimated token budget (~4 chars per token, labelled as an
  estimate; the API's `input_tokens` is the real count and is printed).
- **Voice metrics:** words, estimated speaking time (150 words/min),
  markdown detected (TTS would read `**` or `-` aloud).
- **Eval checks (deterministic, crude by design):** max_words, no_markdown,
  asks_question, must_include_any, must_not_include, no_digits. Categories:
  instruction, concise, followup, ambiguity, restraint. Stage 12 adds
  LLM-as-judge and proper statistics.
